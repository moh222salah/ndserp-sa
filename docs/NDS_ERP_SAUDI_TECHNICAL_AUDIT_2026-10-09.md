## 1. الخلاصة التنفيذية

NDS ERP Saudi مبني على أساس Frappe Framework / ERPNext v16، ويضم تطبيقات الموارد البشرية والمبيعات والمشتريات والمخزون والحسابات ونقاط البيع، إلى جانب طبقة تخصيص عربية، وتكامل الامتثال السعودي، وتطبيقات متخصصة إضافية. المستودع Monorepo ويحتوي على **18 تطبيقًا في bench/apps.txt** وقرابة **18,024 مسارًا** في شجرة GitHub وقت الفحص. حجم المستودع المسجل من GitHub نحو 269,903 KB.

**التقييم العام:** قاعدة تقنية واسعة وقابلة للتطوير، وبها مجهود ملموس في تخصيص الواجهة العربية وإدارة الـWorkspaces والصلاحيات. لكن لا يصح اعتماد نجاح الـCI الحالي دليلًا على أن كل وظائف ERP تعمل بلا أخطاء؛ فالـCI الرئيسي يفحص أغلبه وجود الملفات والنصوص وسلامة JSON وBash، ولا يشغّل اختبارات ERP الفعلية أو دورة متكاملة على قاعدة بيانات وواجهة متصفح.

**الحكم الفني:** صالح كأساس تطوير، لكن اعتماد الجاهزية الإنتاجية يحتاج إلى إغلاق فجوات التحقق والتوافق والأمان ذات الأولوية الواردة أدناه. لم تُجرَ في هذه المراجعة أي كتابة على قاعدة بيانات أو Migration أو تغيير في منطق النظام؛ التغيير الذي يصدر مع المراجعة هو هذا التقرير فقط.

## 3. خريطة المعمارية والتطبيقات

### المنصة الأساسية
- **frappe:** إطار العمل، الـDesk، الـAPI، الجلسات، الصلاحيات، الـHooks والبنية الأساسية.
- **erpnext:** الحسابات، المبيعات، المشتريات، المخزون، الأصول، التصنيع والعمليات المالية.
- **hrms:** الموارد البشرية والحضور والإجازات والرواتب.
- **pos_next:** نقاط البيع وإعداداتها وعمليات الفتح والإغلاق.

### تخصيص NDS والهوية العربية
- **ndserp:** تخصيصات NDS، الـWorkspaces العربية، الـFixtures، إدارة أدوار المستخدمين، وتخصيص تنقل الـDesk.
- **amir_theme_v16:** الثيم العربي/الإنجليزي، RTL/LTR، شاشة الدخول، الخطوط، الـDesk launcher والـheader ومكونات الواجهة.
- **ksa_compliance:** تطبيق الامتثال السعودي والفوترة الإلكترونية وزاتكا.
- **changai / frappe_ai / frappe_vision:** وظائف ذكاء اصطناعي ورؤية/مساعدات مضافة إلى الـBench.

### تطبيقات تخصصية أخرى
**crm، contracting، gas_station، healthcare، optical، optima_hr، nds_restaurant، flow**.

وجود المصدر داخل المستودع لا يعني أن كل تطبيق مثبّت على كل Site أو أن اتصالاته الخارجية مهيأة. في سجل الـmanifest المرفق، ملف `manifest/list-apps.txt` يسجل 11 تطبيقًا مثبتًا على الـSite الموثق، بينما `bench/apps.txt` يحتوي على 18 تطبيقًا متاحًا في المصدر. يجب الحفاظ على هذا الفرق في أي تقرير تشغيل حي أو Deployment checklist.

## 4. المميزات ونقاط القوة

### 4.1 مصدر كود واضح ومزامنة مخصصة للـCodespace
GitHub main هو مصدر الحقيقة المعلن. سكربت `codespace-runtime-sync.sh` يتحقق دوريًا من المصدر بفاصل افتراضي 5 ثوانٍ، ويقارن HEAD مع origin/main، ثم يبني أصول الثيم عند الحاجة ويتحقق من الأصول المولدة. كما توجد `codespace-verify-runtime.sh` للتحقق من البصمة المقدمة من السيرفر. هذا أفضل من الاكتفاء بـgit pull أو Refresh للمتصفح دون التحقق من الأصول.

### 4.2 فصل الثيم في تطبيق مستقل
الثيم يحمّل CSS/JS عبر Hooks مثل `app_include_css` و`app_include_js`، ولديه خطوط عربية مضمّنة محليًا. هذا يدعم قابلية الصيانة، ويقلل الاعتماد على CDN، ويوفر طريقة منظمة لتطوير الهوية المرئية. معظم تعديل الـheader الحديث يقع في SCSS الخاص بالثيم بدل إضافة قواعد عشوائية إلى كل صفحة.

### 4.3 إدارة أكثر انضباطًا لملفات Fixtures
ملف `apps/ndserp/ndserp/hooks.py` يستخدم فلاتر محددة لتصدير Roles وRole Profiles وWorkspaces وProperty Setters وScripts وPrint Formats وReports. هذا يقلل احتمال تصدير سجلات تخص تطبيقات أخرى ثم الكتابة فوقها دون قصد أثناء الـmigrate.

### 4.4 ضوابط صلاحيات على الخادم في الإجراءات الحساسة
منطق `amir_theme_v16/api/smart_actions.py` لا يعتمد على إخفاء الأزرار في الـUI فقط؛ بل يعيد التحقق من صلاحيات المستند ومن صلاحيات الإنشاء/الإلغاء/الحذف، ويمنع إجراء Revert عند وجود Workflow نشط. كما يستخدم عمليات Frappe المعتادة للإلغاء والحذف بدل تغيير حالة المستند بطريقة مباشرة. هذه ضوابط جيدة، مع بقاء الحاجة لاختبارات مالية تكاملية موضحة لاحقًا.

### 4.5 تقييد مدير الوحدة وصلاحيات الـUser
التطبيق `ndserp` يحدد Role Profiles المسموح بها لمدير الوحدة ويقيّد استعلامات User وRole Profile عبر Hooks للصلاحيات. توجد اختبارات في `apps/ndserp/ndserp/tests/test_user_provisioning.py`. هذا أساس جيد، لأن أخطاء هذا المسار قد تتحول إلى تصعيد صلاحيات بين الأقسام.

### 4.6 وجود اختبارات في عدد من التطبيقات
شجرة المصدر تضم ملفات اختبار عديدة من Frappe وERPNext وHRMS وCRM والتطبيقات التخصصية. وبحصر ملفات الاختبار داخل التطبيقات المخصصة، ظهر نحو 126 ملف اختبار Python، و11 اختبار JavaScript بصيغة `.test.*`، و5 اختبارات E2E بصيغة `.spec.ts` ضمن التطبيقات التي تمت مراجعتها. هذا تعداد ملفات، وليس إثباتًا بأن الاختبارات نُفذت أو نجحت.

### 4.7 حدود تشغيل منفصلة عن بيانات الإنتاج في README
README يوضح أن قاعدة الإنتاج وملفاتها الخاصة وملف site_config والبيئة المولدة ليست جزءًا من الاستعادة الافتراضية، ويشرح إعداد أسرار التطوير لاستعادة البيانات عند الحاجة. هذه نقطة جيدة لتقليل الخلط بين بيئة التطوير والإنتاج.

## 5. العيوب والمخاطر مرتبة حسب الأولوية

## P1 — يجب معالجتها قبل اعتبار النظام مختبرًا بالكامل

### P1.1 — الـCI الحالي لا يختبر وظائف ERP الفعلية

الـWorkflow الوحيد الموجود على مستوى المستودع هو `.github/workflows/saudi-codespace-validate.yml`. يختبر JSON، وصياغة سكربتات Bash، ووجود مجلدات التطبيقات، ووجود نصوص معينة في الملفات، و`git diff --check`. لا يشغّل تلقائيًا:
- اختبارات Python الخاصة بالتطبيقات.
- اختبارات Frappe/ERPNext على MariaDB.
- تثبيتًا نظيفًا لكل التطبيقات على Site تجريبي.
- بناء الأصول كاملةً ضمن CI.
- اختبارات JavaScript أو Playwright على صفحات الدخول والـDesk والـWorkspaces.
- فحصًا أمنيًا عامًا للتبعيات والأسرار.

وبالتالي، نجاح Workflow رقم 194 يثبت نجاح هذه الفحوصات المحددة فقط، لا سلامة الوظائف أو توافق قاعدة البيانات.

**الإصلاح المقترح:** بناء CI على مراحل: (1) lint وPython compile وJSON، (2) تثبيت نظيف قابل لإعادة الإنتاج، (3) اختبارات التطبيقات المخصصة، (4) بناء الثيم والأصول، (5) اختبار API والصلاحيات، (6) Smoke/E2E للـLogin والـDesk والـWorkspaces، (7) فحص تبعيات وأسرار. يجب أن تصبح اختبارات `ndserp` و`amir_theme_v16` و`nds_restaurant` و`ksa_compliance` بوابات منع دمج للتغييرات المرتبطة بها.

### P1.2 — تعديلات مباشرة في Frappe Core ترفع تكلفة الترقية

المصدر يحتوي تعديلات مباشرة في:
- `apps/frappe/frappe/auth.py`
- `apps/frappe/frappe/sessions.py`
- `apps/frappe/frappe/www/login.py`
- `apps/frappe/frappe/www/login.html`
- `apps/frappe/frappe/templates/includes/login/login.js`

هذه التغييرات تمرّر اللغة المختارة في صفحة الدخول إلى جلسة المستخدم، وتحفظ اللغة في بيانات الجلسة، وتحدد مصدر لغة قالب الدخول. المقارنة مع المصدر الرسمي عند commit Frappe المسجل أظهرت إضافات فعلية في auth.py وsessions.py؛ لذلك لا يصح وصف النظام كله بأنه لا يعدّل Core، حتى لو كان تطبيق الثيم نفسه يستخدم Hooks مدعومة.

**الأثر:** تعارضات محتملة مع تحديثات Frappe v16، وصعوبة مراجعة التغييرات الأمنية/تغييرات تسجيل الدخول عند كل تحديث، واحتمال رجوع مشكلة اللغة إذا تغيّر عقد الجلسة أو الـLogin flow.

**الإصلاح المقترح:** محاولة نقل أكبر قدر ممكن إلى Hooks أو نقاط تمديد رسمية. إذا كان تعديل الـCore لا يمكن تفاديه، فاحتفظوا به كـpatch موثق ومحدود، مع مرجع upstream واضح، واختبارات سلوكية فعلية تثبت اختيار اللغة العربية والإنجليزية قبل تسجيل الدخول وبعده، واستمرار اللغة عند Refresh وتغيير المسار وتسجيل الخروج، وعدم إضعاف CSRF أو الجلسة.

### P1.3 — بعض Hooks تنفذ تعديلات قاعدة بيانات تلقائيًا عند migrate

في `amir_theme_v16/hooks.py` يوجد `after_migrate` إلى `amir_theme_v16.install.after_migrate`. الوظيفة تستدعي `setup_smart_action_permission_types()`؛ وهذا ينشئ Permission Type عند غيابه، ويضيف Grants أولية للأدوار التي تمتلك الصلاحيات الأساسية. المنطق مصمم ليعمل مرة واحدة لكل Permission Type، لكنه يظل تغييرًا في بيانات الصلاحيات عند الـmigrate.

كذلك `ndserp/hooks.py` يربط `after_install` و`after_migrate` بسياسات الـWorkspace والـSidebar والـRoles. وثائق الكود توضح أن سياسة NDS تخفي الـWorkspaces غير التابعة لـNdserp افتراضيًا بعد التثبيت/الترحيل، مع خيار إعداد لتعطيلها.

**الأثر:** تحديث التطبيق ليس تغيير كود فقط؛ قد يعيد مزامنة Workspaces أو يغير ظهورها ويضيف سجلات/منح صلاحيات. كما أن `ndserp.install.after_migrate` يسجل بعض الإخفاقات في Error Log ويتابع، وهو ما يستلزم فحص السجل بعد الـmigrate وعدم اعتبار اكتمال الأمر وحده دليلًا على نجاح كل سياسة.

**الإصلاح المقترح:** توثيق كل أثر قاعدة بيانات لكل Hook، واختبار الـmigrate على نسخة Staging مستعادة، ومقارنة Roles وPermission Types وCustom DocPerm وWorkspaces قبل وبعد، وإثبات Idempotency وعدم إعادة منح صلاحية ألغى مدير النظام منحها يدويًا. لا تُجرَ هذه التغييرات على الإنتاج دون Backup وخطة rollback.

### P1.4 — إجراء Revert للمستندات المالية مدمر بطبيعته ويحتاج اختبارات تكاملية

تنفيذ `revert_to_draft` في `amir_theme_v16/api/smart_actions.py` يقوم بإلغاء المستند المرسل، ثم حذفه بالطريقة النظامية، ثم إدراج نسخة جديدة كمسودة بالاسم نفسه. الضوابط الحالية تشمل الصلاحيات ووجود Workflow، وهذا جيد؛ لكن تسلسل Cancel → Delete → Reinsert حساس في ERP، خصوصًا للمستندات المرتبطة بالمخزون والأستاذ العام والمراجع الخارجية وسجل التدقيق.

**الإصلاح المقترح:** اختبارات Frappe حقيقية على Sales Invoice وPurchase Invoice وPayment Entry وStock Entry، تشمل القيود المحاسبية وحركات المخزون والمراجع التابعة ورفض الحذف عند وجود روابط، وRollback إذا فشلت الخطوة الأخيرة، والحفاظ على سجل التدقيق والتسلسل المرجعي. لا يُكتفى باختبار أن endpoint يعيد اسم المستند.

### P1.5 — تقييد الـWorkspaces يعتمد على تغليف Methods داخل Frappe وقت التشغيل

`apps/ndserp/ndserp/setup/workspace_scope.py` يغلّف/يستبدل `Workspace.get_allowed_modules` و`Workspace.is_permitted` على مستوى الكلاس ويضع علامة لمنع التكرار. هذا ليس تعديلًا نصيًا في ملف Core، لكنه يعتمد على تفاصيل تنفيذ داخلية في Frappe، وقد يتأثر بتغيير توقيع الدوال أو ترتيب التهيئة أو طريقة بناء الصلاحيات في تحديث لاحق.

**الإصلاح المقترح:** إضافة اختبارات سلوكية تغطي المستخدم العادي، ومدير الوحدة، وSystem Manager وWorkspace Manager، والحالات التي يحمل فيها المستخدم أدوار تشغيل حقيقية مع دور Workspace NDS. يجب إثبات أن إخفاء Workspace لا يفتح أو يغلق صلاحية DocType نفسها وأن عناصر الـSidebar والـBreadcrumb لا تتسرب عبر الوحدات.

## P2 — تحسينات مهمة للاستقرار وقابلية الصيانة

### P2.1 — تفاوت واضح في الاختبارات للتطبيقات المخصصة

تظهر شجرة المصدر أن:
- `amir_theme_v16`: لا توجد ملفات اختبار Python أو JavaScript أو E2E مطابقة لأنماط الاختبار المعتادة.
- `ndserp`: اختبارا Python أساسيان؛ لا يظهر اختبار مخصص مباشر لمسار `workspace_scope`.
- `changai`: 3 اختبارات Python.
- `contracting`: اختبار Python واحد.
- `gas_station`: اختبار Python واحد.
- `optical`: اختبار Python واحد.
- `ksa_compliance`: 8 اختبارات Python.
- `nds_restaurant`: 20 اختبار Python.
- `optima_hr`: 27 اختبار Python.
- `crm`: لديه تغطية أوسع تشمل Python وJavaScript وE2E.

هذه الأرقام لا تقيس جودة الاختبار أو مقدار التغطية، لكنها تكشف مناطق تحتاج حصرًا للتغطية، خصوصًا الثيم والصلاحيات والتوطين وتدفقات الفوترة.

### P2.2 — الاعتماديات ليست قابلة لإعادة البناء بدقة كافية

تبعيات Python في تطبيقات مثل ChangAI تشمل عددًا كبيرًا من حزم LLM وGoogle Cloud وLangChain وTransformers وSentence Transformers وFAISS وOpenCV وPandas وغيرها، وكثير منها بلا تثبيت نسخة دقيقة في metadata المعروض. هذا يجعل نتيجة التثبيت قابلة للتغير بمرور الوقت، ويزيد مدة التهيئة واستهلاك الذاكرة واحتمال تعارض نسخ المكتبات.

سجل أخطاء التشغيل السابق الذي ظهر فيه عدم العثور على `jellyfish` ثم `rapidfuzz` يؤكد أن وجود الحزمة داخل pyproject.toml لا يكفي وحده لإثبات أن بيئة التشغيل الفعلية تحتوي عليها.

**الإصلاح المقترح:** إصدار Lockfile موحد أو ملف قيود مختبر لكل تطبيق، وفحص imports بعد التثبيت، واختبار bootstrap من بيئة نظيفة بالكامل، مع تمييز التبعيات الاختيارية الخاصة بالذكاء الاصطناعي عن التبعيات اللازمة لعمل ERP الأساسي.

### P2.3 — اختلاف توثيق عدد التطبيقات عن قائمة المصدر

README يذكر 17 تطبيقًا، بينما `bench/apps.txt` يسجل 18 اسمًا، من بينها `flow`. كذلك ملفات manifest تصف لقطة بيئية سابقة لا يجب تفسيرها كأنها حالة التشغيل الحالية. يجب تصحيح العدد، وشرح أن قائمة التطبيقات في المصدر تختلف عن التطبيقات المثبّتة على Site، وتوليد هذه القوائم آليًا بدل تحديثها يدويًا.

### P2.4 — المزامنة التلقائية تتوقف عند وجود تعديلات محلية

آلية `codespace-runtime-sync.sh` تفحص وجود أي تغييرات tracked أو staged أو ملفات غير متتبعة؛ وعند وجودها تطبع `SOURCE_SYNC=BLOCKED_DIRTY_WORKTREE` وتتجنب سحب GitHub. هذا يحمي العمل المحلي، لكنه يعني أن ضمان “Codespace لا يعمل أبدًا على Commit قديم” مشروط بأن يكون الـworktree نظيفًا. إذا بقيت ملفات محلية غير ملتزم بها، فلن تصل المزامنة تلقائيًا إلى أحدث main.

**الإصلاح المقترح:** إضافة تنبيه واضح ومستمر عند حالة Blocked، وعرض HEAD مقابل origin/main في فحص صحة واحد، وتصنيف الملفات المولدة التي يجب تجاهلها. لا أنصح بإلغاء حماية الملفات المحلية عشوائيًا أو فرض reset على worktree متسخ؛ الحل الصحيح هو سياسة واضحة تميّز التعديلات المقصودة من الملفات المولدة.

### P2.5 — تحقق الأصول أقوى من السابق لكنه لا يساوي اختبار DOM

التحقق الحالي يقارن ملفات CSS ويبحث عن محددات نصية مثل `body .navbar` و`58px` و`#0a2342`، ويثبت تطابق بصمة CSS المبني والمخدوم. هذا دليل جيد على نشر الملف الصحيح، لكنه لا يثبت وحده أن المحدد يطابق عنصر الـNavbar الفعلي، أو أن قواعد CSS لا تتغلب عليها قواعد أخرى، أو أن النتيجة المرئية سليمة على جميع الصفحات.

**الإصلاح المقترح:** إضافة Playwright بعد تسجيل دخول اختبار آمن، وفحص DOM وcomputed styles للـNavbar على Desk وصفحات Modules، مع قياسات سطح المكتب والموبايل وRTL/LTR. يجب أن يفشل الاختبار إذا حمّل المتصفح أصلًا قديمًا أو إذا كانت قيمة computed style مختلفة عن المطلوب.

### P2.6 — أسرار بيئة التطوير ثابتة في سكربت Bootstrap

`codespace-bootstrap.sh` يحتوي كلمة مرور MariaDB root ثابتة لغرض تهيئة Codespace. لا يوجد دليل في الفحص على أنها كلمة مرور إنتاج، وهي ضمن مسار التطوير؛ لكن تثبيت كلمة المرور في المصدر ممارسة غير مناسبة إذا أعيد استخدام السكربت أو الإعداد خارج الـCodespace.

**الإصلاح المقترح:** قراءة السر من متغير بيئي مخصص أو إنشاء كلمة مرور عشوائية محلية لكل Codespace، والتأكد من ألا تُستخدم تلك القيمة في أي بيئة مشتركة أو إنتاجية.

### P2.7 — أصول غير برمجية داخل جذر المستودع تحتاج مراجعة

يوجد مجلد `upload/` يحوي عدة صور بأسماء WhatsApp وتواريخ، بالإضافة إلى `logo.jpeg` وملف باسم `image`. قد تكون هذه ملفات مقصودة، لكن يجب مراجعة محتواها وسبب وجودها في مستودع الكود والتأكد من عدم احتوائها على معلومات عملاء أو صور تشغيل داخلية غير مقصودة. وجود المستودع كـPrivate يقلل التعرض لكنه لا يغني عن مبدأ تقليل البيانات.

### P2.8 — فحوصات أمان سلسلة التوريد غير مفعّلة مركزيًا

شجرة المشروع تضم ملفات Workflow داخل بعض التطبيقات الموردة، لكن GitHub Actions ينفذ الـWorkflows الموجودة ضمن `.github/workflows/` في جذر المستودع؛ المسارات المتداخلة داخل `apps/*/.github/workflows/` لا تعمل تلقائيًا كـWorkflows مستقلة لهذا الـMonorepo. لا يظهر في Workflow الجذري فحص مركزي لـCodeQL/Semgrep أو تدقيق التبعيات أو اكتشاف الأسرار.

**الإصلاح المقترح:** تفعيل فحوصات أمان على المستودع نفسه، وضبط أقل صلاحيات ممكنة للـWorkflow، وتثبيت Actions الحساسة على commit SHA عند اعتماد سياسة سلسلة توريد صارمة، مع الاستمرار في احترام تراخيص التطبيقات المدمجة.

## 6. ملاحظات خاصة بالمجالات التجارية

### المحاسبة والمخزون ونقاط البيع
وجود ERPNext وPOSNext وامتدادات NDS Restaurant يتيح وظائف عملية واسعة، لكن أي تعديل في إلغاء مستند أو إعادة إنشائه أو ترابط فاتورة البيع بالمطبخ والمخزون يجب اختباره على قيود GL وحركات المخزون والروابط التابعة. لا ينبغي اعتماد هذه التدفقات اعتمادًا على اختبار الواجهة فقط.

### الموارد البشرية
المستودع يضم HRMS وOptima HR، مع اختبارات متعددة في Optima HR. ينبغي تحديد ملكية كل DocType وحسابات الإجازات والحضور والجزاءات ونهاية الخدمة بين التطبيقين حتى لا تتكرر القواعد أو تختلف نتائج الحساب. المراجعة الحالية لم تنفذ مقارنة حسابية فعلية بين الحالات المالية/الموارد البشرية.

### الامتثال السعودي وزاتكا
وجود `ksa_compliance` يثبت توفر كود التكامل في المصدر، لكنه لا يثبت وحده أن كل شركة مسجلة بالشكل الصحيح أو أن الشهادات/المفاتيح صالحة أو أن الفاتورة الحالية اجتازت Sandbox/Production. الاعتماد النهائي يتطلب اختبار مستندات مبسطة وقياسية، QR/XML، الرفض وإعادة الإرسال، وحالات الاتصال الفعلية وفق إعدادات الشركة السعودية.

### الذكاء الاصطناعي والتكاملات
ChangAI وتطبيقات الذكاء الاصطناعي تضيف قدرات مفيدة، لكنها أكبر مصدر محتمل لثقل التهيئة وتغيرات التبعيات. يجب عزل فشل هذه الخدمات الاختيارية بحيث لا يمنع تسجيل الدخول أو الوظائف الأساسية لـERP، والتأكد أن المفاتيح والخدمات الخارجية لا تُستدعى قبل تهيئتها.

## 7. خطة معالجة عملية حسب الأولوية

### المرحلة الأولى — تثبيت الثقة في المصدر والتشغيل
1. تصحيح README من 17 إلى 18 تطبيقًا وتوثيق الفرق بين تطبيقات المصدر والتطبيقات المثبّتة على الـSite.
2. إضافة حالة صحة موحدة تعرض GitHub main SHA وCodespace HEAD وSource marker وCSS/JS hash المخدوم.
3. الإبقاء على فحص الأصول الحالي وإكماله بفحص DOM/computed styles بواسطة Playwright.
4. جعل Workflow الرئيسي ينفذ Python compile وlint وبناء الثيم واختبارات صغيرة بدل فحوصات grep فقط.

### المرحلة الثانية — حماية الوظائف الحرجة
1. إضافة اختبارات سلوكية لتغيير لغة الدخول واستمرار لغة الجلسة.
2. إضافة اختبارات صلاحيات مديري الوحدات ومنع الوصول بين الأدوار.
3. إضافة اختبارات تكامل للإجراء Revert على المستندات المالية والمخزنية.
4. اختبار Hooks الـafter_migrate على نسخة قاعدة مستعادة مع تقرير فرق للصلاحيات والـWorkspaces.

### المرحلة الثالثة — الاستقرار والأمان
1. تثبيت نسخ Python dependencies والتحقق من إعادة بناء البيئة من الصفر.
2. فحص الملفات في upload والتأكد من أنها أصول مقصودة وخالية من بيانات حساسة.
3. إضافة فحوصات CodeQL/Semgrep أو فاحص مكافئ، وdependency audit وsecret scanning.
4. وضع سياسة واضحة لتحديث Frappe/ERPNext: مقارنة upstream، مراجعة كل Core patch، تشغيل Regression suite قبل تحديث أي commit أساسي.

## 10. الخاتمة

أقوى ما في NDS ERP Saudi هو اتساع المنصة والتطبيقات المخصصة، وفصل جزء معتبر من التخصيص داخل تطبيقات مستقلة، ووجود ضوابط خادمية للصلاحيات، ومحاولة عملية لربط GitHub بالمزامنة وبصمات الأصول المخدومة.

أكبر فجواته الحالية ليست نقصًا في عدد التطبيقات، بل **غياب بوابة اختبار متكاملة على مستوى المستودع، وتعديلات Frappe Core التي تحتاج إدارة ترقية صريحة، وآثار Hooks التلقائية على قاعدة البيانات والـWorkspaces، ونقص اختبارات بعض التطبيقات الحساسة**. التوصية هي معالجة هذه النقاط تدريجيًا دون إعادة بناء النظام من الصفر ودون تغيير بيانات أو منطق عمل خارج نطاق كل مهمة.

**حالة المراجعة:** اكتمل الفحص الثابت وتوثيق النتائج. النجاح الكامل على مستوى النظام الحي لا يُعتمد إلا بعد نجاح اختبارات الوظائف والـDOM على نسخة Codespace محددة الـSHA، ثم اختبار قبول منفصل على نسخة Staging قبل أي نشر إنتاجي.
